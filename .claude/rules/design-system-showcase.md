# Витрина дизайн-системы = наш Storybook

Роут `/design-system` (`src/views/design-system/`) — **живой каталог всех переиспользуемых
компонентов**, как Storybook. Он же — **мишень визуальной регрессии**: что не показано на
витрине, то барьер не сторожит.

## Обязательное правило

- **Каждый компонент из `src/shared/ui/` обязан быть на витрине.** Добавляешь новый компонент
  в `shared/ui` — в том же PR добавляешь его демо-секцию в `design-system-page.tsx`. Меняешь
  API/варианты существующего — обновляешь его секцию. PR без витрины для нового `shared/ui`
  считается неполным (как Storybook-story к компоненту).
- **Показывать ВСЕ варианты и состояния** — как набор stories, а не один happy-path:
    - все `variant` (primary / accent / ghost / danger …) и размеры;
    - состояния: обычное, `disabled`, загрузка, ошибка/валидация, пустое;
    - тематизация через атрибуты (`data-faction` player/enemy, `data-outcome`,
      `data-intensity="calm"`) — показать переключение, а не один срез;
    - интерактивные компоненты (Dialog, Select) — с открытым/раскрытым состоянием.
- **Только токены.** Демки красятся семантическими токенами из `token-spec.md`
  (`--color-*`, `--text-*`, `--glow-*`), без хардкода hex/px в разметке витрины.
- **Секции подписаны** именем компонента и, где уместно, именем варианта/состояния —
  чтобы витрина читалась как справочник и как diff в визрегрессии.

## Зачем так

Витрина — единственное место, где человек судит вид, а машина потом энфорсит его вердикт
(визрегрессия вмораживает baseline). Компонент вне витрины = невидим для человеческого гейта
вкуса и для барьера консистентности. Поэтому каталог держим исчерпывающим по определению,
а не по желанию.

Дизайн-процесс целиком — в `CLAUDE.md` (раздел «Дизайн-процесс»); токены — `docs/design-system-theming/token-spec.md`.
