# Ralph Runbook — операционная процедура

Как запускать автономный раннер, что проверить до старта и на какие грабли уже наступали.
Это операционный документ для человека и для агента-помощника; правила для кодер-сессии
внутри петли — в `ralph.md`, они про другое.

## Перед стартом фазы

1. **Конфиг фазы обязан быть в `origin/main`.** Раннер детачит своё дерево на
   `origin/main`, локальных правок он не увидит вовсе:

    ```bash
    # .claude/ralph/ralph.config.json → common.phases[0]
    #   milestone: точное название milestone фазы
    #   branch:    ветка фазы (feature/…)
    ```

    Везти отдельной веткой и отдельным PR, **не смешивая с docs**: 21.07 незакоммиченный
    конфиг фазы 5 уехал в чужой docs-PR (#144), потому что ветку резали от локального main.

    > ⚠️ **Исключение — `gate-env-allowlist.json` (санация env чеков гейта, #188).** В
    > отличие от `ralph.config.json`, allowlist читается по `import.meta.dirname`
    > (`gate-env.mts` — явно-ESM, #403) — то есть из
    > **launch-дерева** (`/root/pixel-tanks`), а НЕ из worktree раннера на `origin/main`
    > (провенанс — в докблоке `gate-env.mts`). Поэтому смердженная правка списка **не
    > действует, пока в launch-дереве не сделан `git pull`**: после мерджа PR, трогающего
    > allowlist, обнови launch-дерево (`git -C /root/pixel-tanks pull --ff-only origin main`)
    > — иначе гейт санирует по старому списку (например, режет переменную, которую только
    > что добавили для e2e). Обратная сторона выбора: код проверяемого PR не может подменить
    > список на детаче своей головы (частичное смягчение #209).

2. **Milestone существует, issues размечены.** Без `complexity:*` роутинг моделей не
   видит карточку (правило #142). Проверить:

    ```bash
    gh issue list --milestone "<название фазы>" --state open --json number,title,labels
    ```

3. **Секреты на месте.** Профиль `prod` требует в `/root/ralph.env` именно
   `RALPH_TG_BOT_TOKEN` и `RALPH_TG_CHAT_ID` (не `TG_*` — на этом сработал fail-closed
   22.07: без пушей прод-режим стартовать отказывается, и это правильно).

4. **Раннер не запущен вторым экземпляром.** Лок есть (`acquireLock`, `core/state-lock.ts`,
   берётся до любых побочек): второй запуск — хоть `start-tmux.sh`, хоть `systemctl start
ralph` — отвергается сам, с проверкой живости pid. Ручная сверка нужна не вместо лока,
   а чтобы увидеть осиротевший монитор прошлого прогона (лок его не покрывает):

    ```bash
    pgrep -af "ralph.js|monitor.js"
    ```

    **Первый запуск после #396 (раскладка по папкам):** свип сирот `sweepOrphanMonitors`
    матчит монитор СТРОГО по новому пути `.claude/ralph/runtime/monitor.js`, а осиротевший
    монитор пред-#396-раннера несёт в cmdline старый путь `.claude/ralph/monitor.js` — под
    свип он не попадёт и продолжит слать deadman-пуши параллельно новому. `pgrep` выше его
    покажет (матчит родовое `monitor.js`); прибить руками до старта:

    ```bash
    pkill -f "\.claude/ralph/monitor\.js"   # только СТАРЫЙ путь, новый (runtime/) не трогает
    ```

## Запуск

Штатный запуск — **управляемый процесс**, не фон из чьей-то SSH/claude-сессии
(Issue #103: первый боевой прогон 20.07 держался фоновым процессом claude-сессии —
работало, но «повезло с деревом процессов», не дизайн). Два варианта, оба независимы
от разрыва SSH:

| Вариант                                | Когда                                      | Команда                                              |
| -------------------------------------- | ------------------------------------------ | ---------------------------------------------------- |
| **A — tmux** (HITL, живой лог глазами) | наблюдаемый прогон, attach и смотришь      | `.claude/ralph/provision/start-tmux.sh [профиль]`    |
| **B — systemd** (полностью AFK)        | «запустил и ушёл», статус через journalctl | `systemctl start ralph` (после установки юнита ниже) |

Оба запускают ровно то же самое (`node .claude/ralph/ralph.js --profile prod`) — разница
только в обвязке процесса и способе смотреть лог. Второй экземпляр отвергнет лок раннера
(`ralph.lock`), какой бы вариант ни был запущен первым.

### Вариант A — tmux

```bash
.claude/ralph/provision/start-tmux.sh prod
```

Скрипт поднимает **отдельную** сессию `ralph` (не смешивает с рабочей сессией `work`,
где окна открывает и закрывает человек) с одним окном на две панели: верхняя —
`ralph.js`, нижняя — `runtime/monitor.js` (дашборд: фаза, submitted, прогресс issues,
открытые PR, порог тишины). Панель монитора дожидается появления дерева раннера (путь
спрашивается у самого раннера, `provision/resolve-worktree-path.mts`) — не дождалась за
5 минут, скажет об этом и выйдет, не подвесив ожидание молча. Обе панели получают
`ralph.env` и запускаются через `bash -c '… exec …'`: после выхода процесса секретов
петли в шелле панели не остаётся.

`tmux attach -t ralph` — посмотреть; `tmux kill-session -t ralph` — остановить.
Скрипт стартует только на чистом месте: увидев живую сессию `ralph`, он различает
«раннер работает» (иди смотреть) и «прогон завершился, шелл остался» (нужен
`kill-session`) — и говорит, что именно делать.

Панель монитора — второй экземпляр рядом с тем, что раннер поднимает detached сам.
Он не мутирует ни state, ни pid-файл, но **не** «безвредный вообще»: deadman-пуши он
шлёт свои, а дедуп у каждого экземпляра в памяти процесса
(`lastDeadmanPushMtime`, `runtime/monitor-panel.mts`) — на каждый эпизод тишины
человек получит ДВА одинаковых алерта. Это плата за живой дашборд, а не сюрприз.

**`--reset`** сбрасывает state на первую фазу конфига **и выходит** — это не запуск.
Нужен, когда state пустой или указывает на прошлую фазу; после него запускать обычной
командой (`.claude/ralph/provision/start-tmux.sh prod` — уже без `--reset`).

### Вариант B — systemd (полностью AFK)

Юнит `.claude/ralph/provision/ralph.service` — установить один раз (юниты не приезжают
штатным деплоем, ставятся руками, как `pixel-tanks-backup.service`):

```bash
sudo cp /root/pixel-tanks/.claude/ralph/provision/ralph.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start ralph
```

`systemctl enable` НЕ делаем, и `[Install]` в юните нет намеренно: автостарт после
reboot поднял бы фазу в обход всего чек-листа «Перед стартом фазы». Ребут ничем не
отличается от падения — раз авто-рестарт после сбоя признан вредным (см. ниже), то и
авто-старт после ребута тоже. Понадобится — заводим `ralph.timer` с `OnBootSec=`.

Наблюдение — `journalctl`, не `tail -f` (`log()` пишет в оба места: `ralph.log` и
stdout, который journald перехватывает):

```bash
journalctl -u ralph -f               # живой лог
systemctl status ralph               # активен/завершился/упал последний прогон
```

**Остановка — `systemctl stop ralph`, и она не бесплатна.** Обработчиков сигналов у
раннера нет намеренно (`process.on('SIGTERM')` снимал бы дефолтное действие сигнала, а
колбэк ждал бы свободного event loop, которого при `spawnSync` на двухчасовую сессию не
бывает — раннер переставал умирать по Ctrl-C, см. `core/orchestrator.ts`). Поэтому
`systemctl stop` убивает процесс мимо `process.on('exit')`: **лок не снимается** (следующий
старт пойдёт через путь «🔓 осиротевший лок», и это событие перестанет быть сигналом о
настоящем `kill -9`), а монитор остаётся сиротой до `adoptMonitor`/свипа следующего
запуска. Останавливать посреди прогона — нормально, просто знай цену; штатный выход из
фазы такой платы не требует.

**`Type=exec`, `Restart=no`** — намеренно (см. «Важный нюанс» ниже). `systemctl start`
возвращает приглашение сразу, во время прогона статус — `active (running)`; по завершении
код 0 даёт `inactive (dead)`, ненулевой — `failed`, и он виден в `systemctl status`, а не
теряется в чьём-то выводе.

**Сколько живёт прогон.** У профиля `prod` в этом репозитории `haltBeforeDeploy: false`
(`ralph.config.json`), то есть петля **не** останавливается после мерджа фазы: она идёт
дальше — до `maxIterations`, до конца списка `phases` или до первого fail-closed стопа.
Юнит, висящий `active` шестой час, — это норма, а не зависание. Хочешь «один прогон
фазы = один `systemctl start`» — ставь `haltBeforeDeploy: true` в профиле (поведение #87)
и держи в голове, что внешнее расписание (cron/таймер) поверх непрерывного режима
запускало бы вторую петлю — её отвергнет лок, но смысла в таком расписании нет.

### Важный нюанс: `Restart=always` противопоказан

В отличие от `ss-local`/`privoxy` (сетевые демоны, `Restart=always` в `provision.sh`
уместен), у ralph остановки чаще всего **осознанный fail-closed стоп**: красный гейт,
тупик `blocked` после трёх кругов ревью, breaker (`maxIterations`/`maxNoProgress`),
мёртвый туннель. Слепой авто-рестарт бился бы об ту же стену по кругу и жёг лимиты API,
вместо того чтобы дождаться разбора человеком. Поэтому ни `ralph.service`, ни
`start-tmux.sh` не перезапускают упавший прогон сами — решение о рестарте за человеком
(`systemctl start ralph` / `start-tmux.sh` заново) либо, в будущем, за умным монитором,
отличающим штатный стоп от сетевого сбоя (research-issue #173, вне MVP).

## Профили

| Профиль      | Гейт                                   | Пуши       | После мерджа                           |
| ------------ | -------------------------------------- | ---------- | -------------------------------------- |
| `playground` | build, lint, lint:fsd, typecheck, test | только лог | сразу следующая фаза                   |
| `prod`       | то же + security, coverage, e2e        | в Telegram | сразу следующая фаза (см. сноску ниже) |

> **«После мерджа» у `prod` — это НАШ конфиг, а не дефолт раннера.** Дефолт (флаг не задан
> либо `true`) — стоп перед деплоем (#87), но в `ralph.config.json` у профиля `prod` стоит
> `haltBeforeDeploy: false`: петля идёт дальше непрерывно. Отсюда и многочасовой прогон под
> `ralph.service`, и грабля «непрерывный prod не подхватывает правки на лету» ниже.

**Лог разведён по боевитости, не по профилю дословно (#386).** Пишет в общий
`ralph.log` (по нему судит deadman о живости боевой петли) только прогон с
`profileName=prod` БЕЗ `--dry-run`. Любой другой запуск — `--profile playground`
и/или `--dry-run` (стандартная проверка правок самого раннера, см. примеры ниже) —
пишет в соседний `ralph.dry.log`, не трогая боевой файл: иначе его штатные маркеры
остановки (⏸/✋/🎉) переводили бы deadman в режим `stopped` (порог тишины `Infinity`)
и слепили бы сторож живого прогона.

С фазы 3 надёжности (#216–#219) `prod` разбирает blocked сам: правки → повторное ревью
моделью не слабее поставившей блок → метку снимает раннер по вердикту. К человеку уходит
только тупик — три ревью подряд, оставившие блок. Человеческий стоп-кран теперь отдельный:
метка **`hold`** проверяется первой, сильнее `blocked`, и раннер её не снимает ни на одном
пути — снять можно только руками (`gh pr edit <N> --remove-label hold`).

## Альтернативный рантайм кодер-сессии — Kimi (#373, фаза 6)

Кодер-сессия по умолчанию — Claude CLI (`adapters.coderRuntime` не задан → `claude`,
`ADAPTER_DEFAULTS`). Рантайм **Kimi** — тот же бинарь `claude` через Anthropic-совместимый
endpoint Moonshot (research: `docs/ralph-mini-framework/research.md`): выбор конфигом, ключ
только из env. Claude-путь при этом не меняется.

**Включить (в `ralph.config.json` профиля или `common`):**

```jsonc
"adapters": { "coderRuntime": "kimi" },
"kimiRuntime": {
    "model": "kimi-k2-0711-preview"           // ОБЯЗАТЕЛЕН — имя модели Moonshot
    // "baseUrl": "https://api.moonshot.ai/anthropic"  // дефолт (междунар.); .cn — для КНР
    // "authTokenEnv": "RALPH_KIMI_AUTH_TOKEN"          // дефолт; имя env-переменной с ключом
    // "fallbackModel": null                            // Claude-fallback НЕ подмешивается (риск #3)
}
```

**Ключ — только из env** (инвариант №11): в env-файле раннера
`export RALPH_KIMI_AUTH_TOKEN=sk-…` (ключ Moonshot). В argv он не попадает
(не светится в `/proc/*/cmdline`); каналы Claude-аутентификации в Kimi-сессии снимаются,
чтобы CLI не ушёл на `api.anthropic.com` мимо Moonshot.

**Смоук вручную** (детерминированная проверка проводки — в `orchestrator.test.ts`, блок
«Kimi-рантайм»; ниже — живой прогон против Moonshot):

```bash
export RALPH_KIMI_AUTH_TOKEN=sk-…                 # ключ Moonshot
# в конфиге: adapters.coderRuntime=kimi, kimiRuntime.model=kimi-k2-…
node .claude/ralph/ralph.js --profile playground --once --dry-run   # проводка без спавна
# затем без --dry-run на тестовой фазе — кодер-сессия стартует и выдаёт дифф
```

**Известное ограничение смоука** (research §«Границы»): маркер API-лимита `API_LIMIT_RE`
провайдер-специфичен (Claude). При лимите Kimi даст другой текст — цикл ожидания его не
распознает, обойдётся как с обычным ненулевым завершением. Для смоука приемлемо;
провайдер-осведомлённый маркер — отдельная задача, не в скоупе фазы 6.

## Альтернативный рантайм кодер-сессии — OpenAI (#374, фаза 6)

В отличие от Kimi (тот же `claude` + endpoint Moonshot), рантайм **OpenAI** — **отдельный
первопартийный бинарь `codex exec`** рядом с Claude, не поверх (research: маршрут (б) —
API OpenAI не Anthropic-совместим, а транслирующий прокси нарушил бы fail-closed тихой
мистрансляцией). Claude-путь при этом не меняется; contract шва тот же — `{code, output}`,
вывод склеивается stdout+stderr и сканируется оркестратором.

**Предпосылка:** установлен и авторизован **Codex CLI** (`codex`) — как `claude` для
Claude-пути. Ключ — только из env.

**Проектные инструкции (#375):** `codex exec` не читает `CLAUDE.md`/`.claude/rules/**` —
он подхватывает файл **`AGENTS.md`** из корня репозитория автоматически (тот же
механизм, каким `claude` читает `CLAUDE.md`). `AGENTS.md` несёт синхронизированную с
`CLAUDE.md` копию проектных конвенций (маркеры `AGENTS-SYNC:START`/`END`, гейт-чек
`docs:agents-drift` красит гейт при расхождении) — общий контракт петли (`ralph.md` +
`ralph.project.md`) в него не дублируется, он приходит текстом промпта сессии, как и у
Claude.

**Включить (в `ralph.config.json` профиля или `common`):**

```jsonc
"adapters": { "coderRuntime": "openai" },
"openaiRuntime": {
    "model": "gpt-5-codex"                     // ОБЯЗАТЕЛЕН — имя модели OpenAI
    // "sandboxMode": "danger-full-access"     // дефолт; более узкие: workspace-write / read-only
    // "authTokenEnv": "OPENAI_API_KEY"         // дефолт; имя env-переменной с ключом
}
```

**Ключ — только из env** (инвариант №11): в env-файле раннера
`export OPENAI_API_KEY=sk-…`. В argv он не попадает (не светится в `/proc/*/cmdline`) —
codex читает его из окружения процесса. Аппрув фиксирован `never` (non-interactive AFK:
`codex exec` при запросе аппрува падает); песочница `danger-full-access` штатна, т.к.
раннер крутится в изолированном worktree (инвариант №3), и нужна для git/npm.

**Смоук вручную** (детерминированная проверка проводки — в `orchestrator.test.ts`, блок
«OpenAI-рантайм»; ниже — живой прогон против OpenAI):

```bash
export OPENAI_API_KEY=sk-…                        # ключ OpenAI
# в конфиге: adapters.coderRuntime=openai, openaiRuntime.model=gpt-5-codex
node .claude/ralph/ralph.js --profile playground --once --dry-run   # проводка без спавна
# затем без --dry-run на тестовой фазе — codex-сессия стартует и выдаёт дифф
```

**Известные ограничения смоука** (research §«Границы»):

- маркер API-лимита `API_LIMIT_RE` провайдер-специфичен (Claude) — при лимите OpenAI
  даст другой текст, цикл ожидания его не распознает (как и для Kimi);
- у Codex нет аналога `--fallback-model`/`--max-turns` (Claude-семантика) — в argv их не
  тащим (research, риск #3); фолбэк-политика — honest-стоп/повторная итерация.

Оба ограничения — вне скоупа фазы 6, кандидаты в отдельные задачи.

## Красный пост-мердж деплой (#163–#167, prod)

С фазы 5 наблюдаемости раннер после мерджа prod-фазы **дожидается итога deploy-workflow**
на смердженном sha и делает **healthcheck прода** (HTTP 200 главной). Если workflow упал/не
досмотрен или прод не ответил — раннер ставит **барьер** `state.deployBlock`, шлёт пуш `⛔` и
останавливается: **следующая фаза не начнётся**, пока барьер не снят. Проверка строго
read-only — раннер `main` и прод не трогает.

Ночной сценарий «пришёл пуш ⛔ про красный деплой»:

1. **Смотри run деплоя** — ссылка в пуше и в `state.deployBlock.url`
   (`.claude/ralph/ralph.state.json`); поле `reason` говорит, что именно красное
   (`workflow failure` / `timeout` / `прод не отвечает` / pending — проверка не досмотрена,
   процесс мог умереть в окне ожидания).
2. **Откат релиза — за deploy-workflow** (`.github/workflows/deploy.yml`), не за раннером:
   `main` он не трогает. Почини прод/деплой обычным путём.
3. **Продолжить после починки** — перезапуск loop с флагом **`--deploy-resolved`**: он
   снимает барьер (единственный способ, как и `hold` — осознанное решение человека, раннер
   сам `deployBlock` не снимает). Барьер допушивается ещё раз на старте, если прошлый прогон
   умер между записью барьера и пушем.
4. **`--reset` при активном барьере отказывает** без `--deploy-resolved` — чтобы сброс state
   по несвязанной причине молча не стёр красный барьер.

## Правки человека в ветку фазы

Если разбираешь PR фазы и правишь его сам, помни про инвариант H3: гейт мерджит, только
когда локальный ref ветки совпадает с головой PR. Иначе — честный стоп с сообщением
«в main уехал бы не тот код, что лежит локально».

- **Правишь в дереве раннера** (`/root/pixel-tanks-ralph`) — только когда прогон
  остановлен, иначе гонка с чини-сессией за `.next`/`node_modules`.
- **Правишь в своём дереве** — после `git push origin HEAD:<ветка>` обязательно
  синхронизируй локальный ref, иначе гейт встанет:

    ```bash
    git fetch origin <ветка>:<ветка>
    ```

Наступал 22.07: закоммитил фикс baseline из своего дерева, запушил — гейт отказался
мерджить, потому что ref ветки в репозитории раннера остался на старом sha.

## Грабли (каждая — из реального прогона)

- **Индексы панелей и окон tmux — не универсальная константа.** Наблюдение прогона 20.07
  в сессии `work`: `work:2.1` было ПЕРВОЙ панелью (то есть самим раннером) — там
  `pane-base-index 1`; на нынешнем VDS `tmux show-options -g` даёт `pane-base-index 0` и
  `renumber-windows off`, и те же адреса означали бы другое. Отсюда два следствия. Первое:
  `send-keys` по индексу в чужую раскладку — лотерея, а при `renumber-windows on` окна
  после `kill-window` ещё и переезжают. Второе: `start-tmux.sh` (см. «Запуск», вариант A)
  индексов не использует вовсе — берёт `pane_id` (`%12`), который tmux выдаёт при создании
  панели, и шлёт по нему.
- **`tail -f` не отдаёт панель по одному Ctrl+C** и молча съедает последующий ввод:
  окно выглядит рабочим, а команды не исполняются.
- **Выход из copy-mode: `q` может прилипнуть к следующей команде** (`qset -a && …`).
  Проверять `#{pane_in_mode}` вместо слепой отправки `q`.
- **Во время прогона не трогать конфиг и milestone'ы.** Конфиг читается один раз в
  `main()`, правка milestone на лету сбивает выборку issue и подсчёт остатка фазы.
- **Непрерывный prod (`haltBeforeDeploy: false`) не подхватывает правки на лету.**
  И `ralph.config.json` (включая массив `phases`), и код `ralph.js` читаются один раз
  при старте процесса. Привычный воркфлоу «дозаказать фазы мерджем конфига в `main`»
  в непрерывном прогоне не сработает: смердженные во время прогона правки процесс не
  увидит — скажет «Все фазы завершены» по устаревшему списку, а фаза, правившая сам
  `ralph.js`, доедет до исполнения только после рестарта. Чинит рестарт loop; при
  включённом `false` планируй состав фаз до старта.
- **Не запускать команды в дереве раннера во время прогона** (`npm run build` и т.п.):
  это гонка с чини-сессией за `.next` и `node_modules`.
- **Вкладка `ralph` во время сессии выглядит мёртвой** — `claude -p` печатает вывод
  только в конце. Судить о жизни по `ralph.log`, дашборду и (с фазы 1) по deadman-пушу.
- **Node печатает `MODULE_TYPELESS_PACKAGE_JSON … Reparsing as ES module` при каждом
  запуске entry — это ожидаемый шум, не ошибка.** Ядро — `.ts`-модули без билд-шага
  (нативный type stripping Node 24), а корневой `package.json` без `"type"` заставляет
  Node переспарсить их как ESM с предупреждением. Ставить `"type": "module"` в корне
  нельзя (тронет Next-часть), а вложенный `.claude/ralph/package.json` с ним сломал бы
  CJS-соседей (`ralph.js`, `monitor.js`). Пока живём с предупреждением; чистое лечение
  (отдельный каталог/`package.json` для TS-ядра или суффикс `.cjs` у entry) — на будущее.

## Что смотреть во время прогона

```bash
tail -f /root/pixel-tanks-ralph/.claude/ralph/ralph.log    # хореография боевого прогона
gh pr list --head <ветка фазы>                              # PR фазы

```

`ralph.dry.log` (тот же каталог) — прогоны `--dry-run`/`--profile playground`, не
боевой; при разборе живой петли смотреть `ralph.log`, не его (#386).

Ключевые маркеры лога: `🔄 итерация`, `🔺 Ревью эскалировано`, `🚦 Гейт`,
`✗ <чек> — красный`, `🩹 Чини-сессия`, `✅ PR #N смерджен`, `🏁 Milestone закрыт`,
`⏸ loop остановлен перед деплоем`, `⛔` — любой fail-closed стоп.

## Кодер-сессия упала — что смотреть (#390)

Ненулевой код выхода `claude -p` в кодер-итерации сам по себе не фатален (issue мог быть
закрыт частично, следующая сессия возьмёт его снова). Но раннер сразу — не дожидаясь
следующей итерации — проверяет дерево и сохраняет вывод упавшей сессии:

```bash
ls -t /root/pixel-tanks-ralph/.claude/ralph/sessions/ | head   # свежие падения, файл <issue>-<ts>.log
cat /root/pixel-tanks-ralph/.claude/ralph/sessions/<issue>-<ts>.log
```

Путь к конкретному файлу — в самом сообщении о падении (`ralph.log` и, в prod, пуш в
Telegram): ищи маркер `⛔ Кодер-сессия Issue #N упала`. Секреты петли (`GH_TOKEN`,
`CLAUDE_CODE_OAUTH_TOKEN`, `RALPH_TG_BOT_TOKEN`, `RALPH_TG_CHAT_ID`) в файле отредактированы
(`***`), как и в остальных местах, где может засветиться вывод чужого процесса.

Два исхода:

- **Дерево грязное** (сессия наработала файлы и не закоммитила) — цикл **остановлен**,
  сообщение называет issue, код выхода, оставшиеся файлы (`git status --porcelain`) и путь
  к логу. Разбери руками: либо доведи и закоммить работу, либо `git checkout .`/`git clean`
  осознанно, и перезапусти раннер.
- **Дерево чистое** — прежнее поведение (fail-open): раннер честно залогировал путь к
  сохранённому выводу и пошёл на следующую итерацию. Если падение подозрительное (не просто
  «issue закрылся, сессия упала на финальном шаге») — тот же файл `sessions/<issue>-<ts>.log`
  подскажет причину постфактум, даже когда деадман/монитор её не поймал.

Каталог `sessions/` гитигнорен (как `ralph.log`/`ralph.state.json`) — чистка руками, файлы
не ротируются автоматически.

## Фиксация находок «найдено после» (#170)

После окончания фазы раннер автоматически записывает находки ревью петли в журнал
(счёт по severity из комментариев PR). Но бывают находки, которые проявляются только
при разборе целой фазы утром или позже — их вносит человек вручную.

**Дешёвый шаг фиксации «найдено после»:**

> ⚠️ `<milestone>` обязан **точно** совпадать с `phase.milestone` из `ralph.config.json` —
> по этому ключу сшиваются авто-половина (`review-loop`) и ручная (`found-after`).
> Сокращённое «Фаза 6» даст found-after-записи, которые не сопоставятся с авто-половиной
> (ровно развал из «Контрольной точки» ниже, только заложенный руками). Точное имя фазы 6:
> `Наблюдаемость ralph · Фаза 6: Метрика находок ревью` — свежее бери из `ralph.config.json`
> (`jq -r '.common.phases[].milestone' .claude/ralph/ralph.config.json`).
>
> ⚠️ Запускать из **дерева раннера** (`/root/pixel-tanks-ralph`) или задать
> `RALPH_REVIEW_FINDINGS_JOURNAL` на его journal — иначе запись уйдёт в journal твоего
> checkout'а, а не туда, куда пишет авто-половина (см. `JOURNAL_PATH`, #237).

```bash
M="Наблюдаемость ralph · Фаза 6: Метрика находок ревью"

# Без привязки к конкретному PR (разбор целой фазы):
node scripts/record-found-after.mjs "$M" <blocker> <major> <minor> <nit>

# Пример: 1 blocker, 2 majors, 0 minors, 3 nits
node scripts/record-found-after.mjs "$M" 1 2 0 3

# С привязкой к конкретному PR (если находка привязана к одному):
node scripts/record-found-after.mjs "$M" 1 2 0 3 --pr 235
```

Запись попадает в журнал `.claude/ralph/review-findings.jsonl` с источником `found-after`.

**Контрольная точка (риск PRD):** если ритуал разбора найденных после мерджа багов не
приживётся за 2–3 фазы — человек вернётся к журналу утром и увидит только половину
находок (ревью петли). Решение честнее удалить журнал, чем верить кривому числу. Признак
— журнал растёт вверху (автоматизированная половина) и застаивается внизу (ручная половина
несколько фаз подряд). Если случилось — завести issue об удалении журнала и вернуться к
нему позже, когда явится стабильный процесс разбора.

## После фазы

- `prod` останавливает петлю после мерджа (стоп перед деплоем) — следующая фаза требует
  нового запуска. Перед стопом раннер дожидается итога деплоя и healthcheck прода; красный
  итог ставит барьер (см. «Красный пост-мердж деплой»), снимаемый только `--deploy-resolved`.
- Доска синхронизируется сама (`scripts/project-sync.mjs`, #199), milestone закрывается
  раннером. Если что-то разъехалось — `npm run project:sync`.
- Ревью фазы живёт в комментариях PR. Если ревью запускалось из сессии-помощника —
  публиковать его в PR, а не оставлять в контексте: иначе для команды его не существует.
